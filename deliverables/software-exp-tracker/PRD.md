## 二、产品定义

### 2.1 一句话定位

**一个完全跑在本地浏览器里的冒险岛升级效率记录器——共享游戏画面即可自动读取经验与金币，实时算出经验/小时、金币/小时，并沉淀可回溯的历史记录。**

### 2.2 目标用户

| 用户类型 | 特征 | 核心诉求 |
| --- | --- | --- |
| 主用户：冒险岛练级党 | 长时间挂机/刷怪升级，关注升级速度 | 想知道「现在这一小时效率到底多少」「换地图/换装备后效率有没有提升」 |
| 次用户：追求极限效率的玩家 | 会对比不同路线、装备、Buff | 需要阶段效率趋势 + 历史记录横向对比 |
| 潜在用户：回归玩家 | 想量化自己回归后的升级节奏 | 低门槛：共享窗口 → 校准 → 开始，不想手动记账 |

### 2.3 产品目标（3 个正交目标）

| 编号 | 目标 | 可衡量标准（验收口径） |
| --- | --- | --- |
| G1 | **零手动**：连接游戏窗口后自动、连续地读取经验与金币数据 | 稳态下无需任何手动输入即可持续产出采样点；单次记录中断次数 ≤ 用户可接受（待确认阈值） |
| G2 | **实时可信**：把原始读数转化为玩家能看懂的实时效率指标 | 控制面板持续显示「经验/小时」「近 60 秒 vs 全程平均差值」，且明确区分「已确认/待确认」区间，不产生误导性数字 |
| G3 | **可回溯**：每次记录自动沉淀为历史总结，支持导出/导入 | 每完成一次记录即在历史页生成一条总结；导出后可再导入且数据一致；数据全程仅存本地 |

### 2.4 核心价值

- **不联网、不上传**：游戏画面仅在本机处理，规避隐私与封号顾虑。
- **不手动**：OCR 自动读数，解决「边玩边记账」的痛苦。
- **可信的实时效率**：不是简单除法，而是有「确认机制」来避免经验跳变导致的失真。

## 三、用户故事

| 编号 | 角色 | 我想要 | 以便 |
| --- | --- | --- | --- |
| US-1 | 练级玩家 | 第一次打开工具时，通过「共享当前屏幕/窗口」选中游戏窗口并看到「已连接」 | 我知道工具已经能读画面了 |

| US-8 | 练级玩家 | 在设置里调整识别性能档位（低/中/默认/高/超高）与采集、画面检查频率 | 我能在低配机器上降负载，在高配机器上提精度 |

## 四、需求池（P0 / P1 / P2）

> P0 定义为**能跑通最小闭环**：`连接游戏窗口 → 校准 → 开始记录 → 看到实时效率 → 结束记录 → 历史里能看到这条记录`。

### 4.1 P0 — Must Have（最小闭环）

| 编号 | 模块 | 需求 | 说明 / 验收点 |
| --- | --- | --- | --- |
| P0-1 | 全局 | 应用壳：顶部 tab 导航 = 控制面板 / 识别校准 / 历史记录 / 更新日志 / 设置 | 排除地图排行、关于 |
| P0-2 | 控制面板 | **三步引导**：①选择游戏窗口 → ②需要时校准 → ③开始记录 | 步骤态可视，未完成上一步不可进入下一步 |
| P0-3 | 控制面板 | 通过 `navigator.mediaDevices.getDisplayMedia` 共享窗口，并在视频流上绘制到 canvas 供 OCR 采样 | 断开共享需可重新选择；必须 http://localhost 访问 |
| P0-4 | 控制面板 | 经验进度显示：等级、当前经验、百分比、本级所需经验、距升级 | 数据来自 OCR |
| P0-5 | 控制面板 | 记录控制：开始记录 / 暂停 / 继续 / 结束记录，状态：记录中 / 已暂停 / 已结束 / 正在结束 / 正在保存 | 状态机见 §6.2 |
| P0-6 | 控制面板 | 实时速率：`经验/小时`、`金币/小时`、`记录时长`、`净经验` | 仅在数据「已确认」区间内计算，避免跳变失真 |
| P0-7 | 控制面板 | 速率对比：显示「近 60 秒：」与「全程平均：」及「差值：」；偏差达 **4%** 显示箭头（升/降），回落至 **2%** 后延迟 **1.5 秒** 隐藏 | 阈值与延迟为原站行为，需保留 |
| P0-8 | 控制面板 | **确认状态机文案**：「等待读数」「积累样本」「确认中」「上次确认」「跨级经验缺失」，以及异常提示：「经验变化未能在确认时间内完成核对」「确认期间采集连续性中断」「有一段经验未能确认，因此暂不显示本场净经验」「恢复后效率只统计恢复后的连续区间」「恢复起点」 | 这是可信度的核心，必须实现状态可视化 |
| P0-9 | 控制面板 | 识别失败态：「画面暂不可读」「等待新的清晰读数」「请保持游戏画面可见」 | 用于替代假数据 |
| P0-10 | 控制面板 | 金币数据卡片：显示金币余额（来自背包区域 OCR） | 与经验共用采样管线 |
| P0-11 | 控制面板 | 运行状态区块：画面读取状态、数据更新状态 | 给用户「工具在工作」的反馈 |
| P0-12 | 控制面板 | 效率水平分档文案：「较低水平」「中间水平」「较高水平」「高效水平」 | 用于趋势图/效率评价标注 |
| P0-13 | 识别校准 | 框选区域：经验条、金币、HP/MP；调整后**自动保存** | 区域以画面相对坐标存储（见 §5.3） |
| P0-14 | 识别校准 | 按钮：「自动识别」「全部恢复默认」；提示「请先回到控制面板选择游戏窗口」 | 未选窗口时禁用框选 |
| P0-15 | 识别校准 | 定位状态文案：「识别中」「已定位」「未定位」「正在确认各项位置」「缺少有效的界面定位」「文字无法解析」「文字数值与血条比例不一致」 | 校准置信度可视化 |
| P0-16 | 历史记录 | 列表展示每次记录的核心总结 | 副标题「每次记录的核心总结都保存在当前设备」 |
| P0-17 | 历史记录 | 空状态：「还没完成的记录」/「结束一次实时记录后，核心总结会出现在这里」+ 入口链接「实时记录」 | — |
| P0-18 | 历史记录 | 按钮：导出记录 / 导入记录 / 清除所有记录 | 导出为 JSON 文件 |
| P0-19 | 本地存储 | 数据持久化到 IndexedDB（记录/采样点）或 localStorage（配置） | **不上传任何数据** |
| P0-20 | 设置 | 识别性能档位：低 / 中 / 默认 / 高 / 超高，联动「屏幕采集频率」「画面检查频率」（默认每秒 1 次） | 只保留识别性能相关设置 |
| P0-21 | 设置 | 重置与恢复：恢复出厂设置 | — |
| P0-22 | 非功能 | 纯前端本地应用；OCR 完全在浏览器本地运行；目标 Chrome / Edge 最新版 | 见 §7 |

要点：

- 「自动识别」尝试自动定位各区域；失败时给出「缺少有效的界面定位」「文字无法解析」「文字数值与血条比例不一致」等定位状态。
- 「全部恢复默认」清空所有框选。

档位与频率的建议映射（待架构师确认实际实现，见 §6）：

| 档位 | 采集频率 | 画面检查频率 | 预期用途 |
| --- | --- | --- | --- |
| 低 | 0.5 次/秒 | 0.5 次/秒 | 低配机 / 降 CPU |
| 中 | 1 次/秒 | 1 次/秒 | — |
| 默认 | 1 次/秒 | 1 次/秒 | 出厂值 |

| `status` | enum | `recording` / `paused` / `ended` / `finishing` / `saving` |

### 6.2 记录状态机 `RecordStatus`

```
idle ──开始记录──▶ recording ──暂停──▶ paused ──继续──▶ recording
                        │                  │
                        └────── 结束记录 ───┘
                                   │
                                   ▼
                              finishing ──▶ saving ──▶ ended
```

| 状态 | UI 文案 | 说明 |
| --- | --- | --- |
| `idle` | 未开始 | 未开始记录 |
| `recording` | 记录中 | 正在采集与统计 |
| `paused` | 已暂停 | 停止计入时长与净经验，但保留共享画面 |
| `finishing` | 正在结束 | 停止采集，等待最后一次确认核对 |
| `saving` | 正在保存 | 写入 IndexedDB |
| `ended` | 已结束 | 生成历史总结 |

## 七、非功能需求

| 类别 | 要求 |
| --- | --- |

## 八、待确认问题（含头号风险）

### 8.1 ⚠️ 头号技术风险：浏览器内 OCR 读取游戏画面

**风险描述**：本项目最大的技术不确定性在于——**在浏览器里，仅靠共享画面（getDisplayMedia → canvas）能否稳定、准确地读出游戏界面中的经验数值与经验条进度**。这直接影响 P0-4 / P0-6 / P0-8 全部核心指标的可行性。

**需要决策的方案选项**（建议架构师评估后二选一或组合）：

| 方案 | 原理 | 优点 | 缺点 / 风险 |
| --- | --- | --- | --- |
| A. Tesseract.js 识别数字 | 对经验数值文本框做 OCR，直接拿数字 | 语义明确，能直接得到「经验值」 | 字体/描边/抗锯齿影响大；中文/数字混合可能误识别；每帧 OCR 开销高，实时性差 |
| B. 经验条像素填充比例计算 | 定位经验条区域，统计填充像素占比 × 本级所需经验 | 计算轻量、适合高频次；对字体不敏感 | 需要预先知道「本级所需经验」；升级瞬间比例归零导致跨级断层；颜色/渐变/动画干扰 |
| C. A + B 互相校验（推荐评估） | 数字读数与比例推算交叉验证 | 可信度最高，可产出「置信度」支撑确认状态机 | 实现复杂度最高，需定义不一致时的取舍策略 |

**建议**：**优先评估方案 C**（数字 OCR + 像素比例互校验），因为 PRD 中的「确认中 / 经验变化未能在确认时间内完成核对 / 文字数值与血条比例不一致」等状态，本质上就是在处理两种读数不一致的情形——原站很可能正是双源互校验。若实现成本过高，退化为 B 为主 + A 定期抽检。

## 九、交付范围小结

| 优先级 | 内容 |
| --- | --- |
| **P0** | 应用壳 + 三步引导 + 窗口共享 + 经验/金币/速率实时面板 + 确认状态机 + 校准页 + 历史记录（含导出导入）+ 本地存储 + 识别性能设置 |
| **P1** | 效率趋势折线图 + HP/MP 卡片 + 记录详情 + 导入合并策略 + 中断恢复 |
